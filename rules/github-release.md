# GitHub 版本、打包与发布规则

## 定位

本文是本项目版本管理和桌面包发布的唯一流程规则。实际自动化见 [build.yml](../.github/workflows/build.yml)，版本与构建配置见 [package.json](../package.json)。规则中的人工检查必须执行；不能据此宣称 GitHub 已配置分支保护或自动门禁。

## 1. 分支和触发行为

| 事件 | 当前行为 | 下载位置 |
|---|---|---|
| 推送到 `main`，包括仅文档修改 | 测试并构建 Windows x64、macOS x64、macOS arm64；跳过发布任务 | 对应 Actions run 的 Artifacts，保留 30 天 |
| 推送 `v*` 标签 | 三个平台构建成功后校验版本，创建 GitHub Release 并上传附件 | Releases |
| 手动运行工作流 | 按所选 ref 构建；若 ref 是 `v*` 标签，也会进入发布任务 | 取决于 ref |
| 普通分支推送或 PR | 当前工作流未配置自动触发 | 无自动产物 |

- `main` 是集成分支，允许自动构建开发快照。每次推送不自动升级版本，也不自动生成 Release。
- 新工作分支默认使用 `codex/<主题>`；提交保持范围清晰。直接推送 `main` 应符合当前任务授权和仓库实际权限。
- 用户授权推送代码不等于要求立即创建新版本。只有任务包含发布版本时才执行版本升级、标签推送和公开发布；已有明确发布授权不重复确认。
- 排查“没有下载包”时先核对 ref、提交 SHA、各构建任务和 Release 任务状态，再检查 Artifacts 或 Releases。

## 2. 版本和标签

- `package.json.version` 是应用版本来源；`package-lock.json` 顶层及 `packages[""].version` 必须一致。
- 正式发布标签固定为 `vX.Y.Z`，必须精确等于 `v` 加应用版本。不要使用 `vlatest` 或复用旧标签。
- 补丁版本用于兼容性修复；次版本用于新增功能；稳定期主版本用于破坏兼容的变化。`0.x` 阶段出现破坏兼容的变化时升级次版本，并在说明中列出影响和迁移方法。
- 纯文档或 CI 维护不必单独升级应用版本；准备交付新的应用包时统一确定下一版本。
- 可以使用 `npm version <明确版本> --no-git-tag-version` 同步两个 JSON 文件，审查差异后单独提交。禁止用不带该选项的命令提前自动创建标签。
- 当前工作流没有 prerelease 标记和 Latest 选择逻辑。发布 `-alpha`、`-beta`、`-rc` 版本前，必须先实现并验证预发布流程，不能直接推送此类标签当作普通发布。
- 已发布标签及二进制附件保持不可变；修复应用或构建内容必须使用新版本。禁止移动旧标签、强推标签或静默覆盖已有附件。

## 3. 发布前检查

1. 明确本次版本、变更范围和发布授权；检查本地状态及远端 `main`，避免把其他任务的未完成改动纳入发布。
2. 核对版本和锁文件；更新受影响的中英文 README，准备中英文发布说明：新增、修复、兼容性影响、已知问题、签名状态和硬件验证范围。无需为不存在的变更填写空章节。
3. 运行 `npm ci`、`npm test` 和 `git diff --check`；行为变化补充必要的针对性测试。涉及桌面启动、网络服务或 PS5 通信的变化，还要记录相应人工验证及未覆盖平台。
4. 提交并推送本次确定的代码；确认远端 `main` 上目标提交的 Windows x64、macOS x64、macOS arm64 三个构建全部通过。必须核对完整提交 SHA，不能仅凭最近一次绿色状态判断。
5. 从已验证、已进入远端 `main` 的提交创建带说明的版本标签，只推送本次明确的标签，不使用 `git push --tags` 批量发布无关标签。
6. 标签工作流会重新构建。跟踪这一次运行直到构建和发布任务全部结束，再执行发布验收。

若共享工作区存在无关改动，应使用干净的发布检出或明确的已提交 SHA；不得临时塞入、丢弃或冒用其他任务的改动。

## 4. 构建及附件合同

- CI 使用 Node 22、`npm ci` 和仓库锁文件；各平台先执行 `npm test` 再打包。依赖下载失败不得通过跳过测试或移除锁文件绕过。
- Windows 使用 NSIS 安装包和 portable 可执行文件；macOS 分别构建 Intel 和 Apple Silicon 的 DMG、ZIP。
- 应用包来自同一次标签工作流。禁止混入本地旧 `dist/` 文件、其他提交或其他 run 的产物。
- electron-builder 打包步骤保持 `--publish=never`；公开发布由工作流的 Release 任务统一负责。
- 公共构建不依赖本机 Nexus 凭证、个人绝对路径或本地证书。未来接入签名时使用 GitHub Secrets，并同步更新工作流和使用说明。
- 当前包未经代码签名，macOS 未公证。发布说明必须明确，不得称其已签名、已公证或已完成所有实机验证。

每个 Release 必须包含以下 7 个自行上传的附件，其中 `<版本>` 不带 `v`：

| 平台 | 附件 |
|---|---|
| Windows x64 安装包 | `PS5-Local-Host-<版本>-windows-x64-setup.exe` |
| Windows x64 便携包 | `PS5-Local-Host-<版本>-windows-x64-portable.exe` |
| macOS Intel | `PS5-Local-Host-<版本>-macos-x64.dmg`、`PS5-Local-Host-<版本>-macos-x64.zip` |
| macOS Apple Silicon | `PS5-Local-Host-<版本>-macos-arm64.dmg`、`PS5-Local-Host-<版本>-macos-arm64.zip` |
| 校验清单 | `SHA256SUMS.txt`，覆盖上述六个应用包 |

GitHub 自动附加的 Source code ZIP/TAR 是源码归档，不是可直接安装的应用包，不计入上述 7 个附件。

## 5. 发布验收与说明

- 确认标签指向预期提交，标签与包内版本一致，三个构建和 Release 任务全部成功。
- 打开实际 Release 页面，确认已公开发布、不是草稿，六个应用包及校验清单齐全、文件大小非零。
- 下载发布后的校验清单及六个附件并核对 SHA-256；上传前校验不能代替发布后的下载验收。校验和证明文件一致性，不等于签名或功能验证。
- 发布前必须提交 `.github/releases/vX.Y.Z.md` 双语说明；工作流使用与标签对应的文件，缺失时停止发布。说明保留实际签名状态、第三方组件边界和未验证事项。发布后工作流自动下载七个附件，比较校验清单并核对六个应用包的 SHA-256；仍需检查实际 Release 页面及任务结果。
- 报告版本、提交 SHA、Actions 链接、Release 链接及检查结果。只有推送成功或只有 Artifacts 时，不能报告“版本已发布”。

## 6. 失败与恢复

- 构建失败：查看失败 job 的日志并定位原因。临时网络或 runner 故障可重跑同一提交；涉及代码或工作流修复时使用新的提交，已经推送的版本标签不移动。
- `main` 构建失败不会修改已有 Release。修复后重新验证目标提交，不以已有版本可下载为当前构建成功的证据。
- Release 任务失败：先检查是否已创建草稿、是否只上传部分文件。当前 `gh release create` 流程并非可无条件重复执行；已有同名 Release 时禁止盲目重跑或使用 `--clobber`。
- 未公开的草稿可在确认标签、提交和原始产物一致后补齐并校验；涉及删除草稿或附件时，应有明确恢复授权。已公开的错误版本通过发布说明标明问题，并发布修复版本，不重写历史。
- 包可以下载但运行或实机测试失败时，应报告该失败并修复；禁止用构建绿色状态覆盖运行结果。

## 7. 权限和规则维护

- 构建任务保持 `contents: read`；仅 Release 任务授予 `contents: write`。发布使用工作流的 `GITHUB_TOKEN`，不把个人 token 写入仓库。
- 未受信任的 PR 不得获得发布凭证；后续增加 PR 检查时必须保留此边界。
- 修改触发条件、平台矩阵、附件命名、签名策略或版本规则时，同步更新本文件、工作流及受影响的中英文使用说明。
- 本文件定义操作约束；当前 CI 只自动执行工作流中已有的校验。分支保护、锁文件版本一致性、标签所属分支和中英文发布说明审核不能假定已有自动检查。
